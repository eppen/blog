Luban vs DeepSeek Harness：同一批任务跑 56 次，成本差距到底在哪

发表于2026-11-10|更新于2026-11-10|技术
|浏览量:

手上有两个编码 Agent：自己写的 Luban（VS Code 侧边栏那套），和 DeepSeek 官方的 dsh（DeepSeek Harness 的命令行版）。一直想搞清楚一个很实际的问题——

同样的模型、同样的代码库、同样的任务，到底谁更划算？

于是拿一套真实在跑的企业系统（Java + Spring + nginx + CAS，约 1.4 万个源文件）当语料，设计了三轮递进的对比实验，一共跑了 56 次。

实验设计

前提条件先把变量卡死：

项 设置
模型 两边都锁 deepseek-flash（同一把 key，计费口径一致）
代码语料 同一份源码副本，各 280MB，排除 target/node_modules/.git
工作区 每次运行前重新 clone，互不污染
上限 600~900 秒看门狗，超时即杀
并发 两个工具各一条 lane 并行，同一时段、同机器，环境对等

三轮任务从”读”到”写”再到”必须编译通过”：

  1. 第一轮：3 道只读的定位/分析题
  2. 第二轮：扩到 10 题（4 只读 + 6 可写），每题跑 2 轮取中位数
  3. 第三轮：5 道硬题，必须 mvn compile 通过才算过

计费用”等效单位”换算，因为两个工具的 token 上报口径不一样：

等效计费 = 新输入 × 1 + 缓存读 × 0.1 + 输出 × 1

（DeepSeek 缓存命中的价格约为新输入的 1/10，这个折算能反映真实账单量级。）

第一轮：3 道只读题，两个 Agent 都纠正了我的错误

第一轮里我埋了个”坑”——其中一道题的前提是错的。

题面是：”MES_CAS_ENABLED=true 时，请求 /mes-web/sys/user/list 带一个随手编造的 token 也可能返回 200，为什么？”

我当时的判断是”EOS 集成兜底放行了任意 token”。两个 Agent 都没顺着我说，而是直接推翻了这个前提：

  • 真正的 200 不是鉴权被绕过，而是 OAuth2Filter 的两个失败分支只往 body 里写 {"code":401}，整类里没有一处 setStatus —— Servlet 默认状态码就是 200
  • 另外还有一处 fail-open：getRequestToken 只认 header token、query、Cookie mes_token 四个位置，**不认 Authorization: Bearer**；伪造 token 放错位置就被当成”没带 token”，直接沿用已有 Shiro 会话放行

我事后实测验证：-H "token: invalid123" 返回 HTTP 200 + {"code":401,...}，且 OAuth2Filter 里 setStatus|sendError 出现次数为 0。两个 Agent 的诊断都对。

正确性：15/15 打平。差距全在成本——**Luban 约为 dsh 的 54%**，而且几乎全集中在最难的那道 t2 上（414k vs 810k，258 次工具调用 vs 79 次）。

第二轮：扩到 10 题，规律反过来了

第一轮的结论是”Luban 更省”，但样本太小。于是扩到 10 题：4 道只读（定位、配置汇总、枚举全部注册过滤器、token 生命周期），6 道可写（抽常量、加接口、改 nginx 负载、WebSocket 走 upstream、加 gzip、补 401 状态码），每题各跑两轮取中位数。

任务 Luban 计费 dsh 计费 dsh/Luban
r1 定位过滤器注册 23,218 14,200 0.61
r2 nginx 配置汇总 19,352 15,263 0.79
r3 枚举全部 Filter 21,476 26,732 1.24
r4 token 生命周期 81,803 224,080 2.74

w3 加 /mes-report/ 负载 49,780 31,177 0.63

w6 补 401 状态码 26,450 11,829 0.45
合计 400,123 442,118 1.10

总分看是 1.10 倍基本持平，但拆开看规律就清晰了：

场景 谁更省 倍数
只读 4 题（读代码、跨文件分析） Luban dsh 是它的 1.92 倍
可写 6 题（定点改文件） dsh 只要它的 0.64 倍

最典型的是 r4：dsh 翻了 112 次工具、22.4 万计费；Luban 26 次调用、8.2 万就收敛了。反过来 w6（补个状态码）dsh 9 秒 1.2 万，Luban 18 秒 2.6 万。

两家策略不同：Luban 先建索引再精读，dsh 倾向大范围 grep/read 地毯式扫。所以”读懂”的活 Luban 划算，”动手”的活 dsh 划算。

意外发现：单次结果不可信

同一题跑两次，耗时能差三倍：

  • w3 的 Luban：32s ↔ 97s
  • w5 的 dsh：21s ↔ 86s

只看一次很容易得出相反结论。这也是为什么每题必须跑两轮取中位数。

第三轮：5 道硬题，加编译门禁

前两轮的题都只要”写出正确内容”。第三轮换成必须真改代码的题，判分加了硬门禁：**mvn -o -pl <模块> -am compile 必须通过**，再叠加 4~6 项结构/语义检查。

结果：加了编译门禁，两边依然全过。差异只剩成本——dsh 是 Luban 的 2.2 倍计费、2.8 倍耗时。

极端个案是 h4（给 Shiro 注册加个开关）：dsh 花了 385 秒、32.7 万、136 次工具调用；Luban 32 秒、3.2 万。同一道题差 10 倍。

语义抽查：不只看关键词

判分脚本容易被”结构像”糊弄，所以我人工比对了真实 diff：

  • h2 Luban：if (StringUtils.isBlank(token) || token.trim().length() < 8) return null;，并且查询仍用原值 token，注释还解释了为什么用 trim 长度判断——比我要求的更严谨
  • h2 dsh：token.length() < 8，逻辑等价，同样正确
  • h1 dsh：确实删掉了 CasController 里的 @Value("${spring.cas.enabled:false}") private boolean casEnabled，改为注入新组件

三轮汇总

轮次 运行次数 正确性 成本结论
只读 3 题 6 15/15 = 15/15 Luban 省 46%
扩样本 10 题 ×2 40 40/40 全满分 只读 Luban 省一半；可写 dsh 省 36%
硬题 5 题 10 编译 10/10、检查全过 dsh 贵 2.2 倍

合计 56 次运行，0 失败、0 超时。

方法论反思：判分脚本坑了自己三次

这轮最值得记的不是”谁更强”，而是评测本身的坑：

问题 后果 处理
h3 题面写”改 SysUserTokenRedis“，字面量其实在 RedisKeys 两个 Agent 都改错目标文件 改题面后重跑
h4 判分只认 :true 写法，不认 @ConditionalOnProperty(matchIfMissing=true) 误杀正确答案 修正判分，用保留的工作区重判
h5 比对片段写成 jpg|png|js|css（原串是 js|css|png|jpg） 误杀 同上
h3 判分等式 raw == consts 不可能成立 误杀 同上

四条里有三条是判分器错、不是 Agent 错。所以结论是：**自动化评分必须能”用保留现场重判”**——我这次每次运行都留下完整工作区，才做到改完判分规则直接把历史结果重算，不用重跑 Agent（只有题面错误的那一次真的重跑了）。

天花板效应

必须承认一个局限：三轮下来，两边都是满分。

这说明 deepseek-flash 这个档位对两个 harness 都不是瓶颈——题目再”硬”，也只是在吃 token，测不出能力上限。要真正拉开差距，得换维度：

  1. 必须跑起来验证：写单测、起服务打接口、改完 nginx 跑 nginx -t 加真实转发
  2. 换更强的模型（比如 deepseek-v4-pro），现在两边都被 flash 的能力压平了

复现

最后

如果只记一句话：

在同一个模型下，harness 的差异不在”能不能做对”，而在”用什么代价做对”。
读代码找答案，Luban 便宜一半；对着明确目标改一处代码，dsh 更干脆；任务一复杂，dsh 的探索成本会成倍放大（h4 那道题 10 倍差距就是例子）。

下一轮打算加”必须跑起来验证”的题——那才是真正能分出高下的地方。
