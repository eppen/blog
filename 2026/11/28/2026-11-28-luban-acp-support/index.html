Luban 现在能在 Zed 和 JetBrains 里用了：聊聊 ACP 支持

发表于2026-11-28|更新于2026-11-14|技术
|浏览量:

一句话

Luban 加了 ACP（Agent Client Protocol）支持。同一个内核，现在除了跑在 VS Code / VSCodium 侧边栏和终端 CLI 里，也能被 Zed、JetBrains 这类编辑器当成自己的编码 agent 来驱动 —— 正文、思考、工具卡片、计划都是客户端原生渲染，写文件前会把 diff 交给客户端的权限弹窗确认。

内核一行没改。

ACP 是什么，以及它不是什么

先说清楚一件事：ACP 是一层传输协议，不是新能力。

它解决的问题是「编辑器怎么跟一个外部编码 agent 说话」。以前每家编辑器都得为每个 agent 写一套私有集成；有了 ACP，agent 只要实现一遍协议，就能进所有支持它的客户端的安装列表。Zed 和 JetBrains 现在共用的就是这套接口。

所以给 Luban 加 ACP，没有增加任何编码能力 —— 工具循环、预算闸门、审阅、多 provider 这些都是原来就有的。它增加的是一个分发入口：注册一次，就同时进了 Zed 和 JetBrains 的 agent 列表。

为什么实现起来几乎不费力

这事儿能这么快做完，靠的是两个早就打好的底子。

第一，runAgent 本来就能在没有编辑器的进程里跑。 Luban 的 CLI 早就证明了这点 —— 它把 require('vscode') 桩掉，agent 循环照样能跑。所以「脱离 VS Code 扩展宿主」这件事不是从零开始。

第二，runAgent 的回调基本就是 ACP session/update 的枚举。 看一眼这两边的对应关系：

Luban 内核回调 ACP 通知
onToken agent_message_chunk
onReasoning agent_thought_chunk
onTool（start / end） tool_call / tool_call_update
onTodos plan
confirmWrite / askWait session/request_permission

回调的形状和协议的形状几乎一一对应。所以 acp.js 这个新文件只负责两件事：在 stdio 上收发 JSON-RPC，以及把内核回调翻译成 ACP 通知。内核一行没动。

怎么接（以 Zed 为例）

Zed 设置（Ctrl+, / Cmd+,）里加一个 agent：

从 npm 装过包的话，command 直接写 luban-acp（发布态的 dist/acp.js，需 Node 18+）。

几个容易踩的点：

  • Windows 路径要转义：JSON 里反斜杠得写成 \\，或者直接用正斜杠 "args": ["d:/Tools/luban/acp.js"]
  • 改完不用重启 Zed：它自动检测 settings.json 变化
  • **密钥走 env**：Zed 起子进程时会继承你的 shell 环境，已经 export 的 key 直接可用；否则填进 env 字段。这段是个人配置，别提交进仓库
  • 排错：命令面板跑 dev: open acp logs，能看到 Zed 与 agent 之间的完整 ACP 消息

配好之后，在 agent 面板的 + 菜单里选 Luban 就行。

JetBrains 的接入项同样是指定「启动命令 + 参数」，填 node <repo>/acp.js 即可。

客户端里能看到什么

因为渲染完全交给客户端，你在 Zed 里看到的是它的原生 UI：

  • 正文流：模型输出实时流式显示，收尾总结（撞轮数 / 墙钟那段）也补在同一条流里，不重复不漏
  • 思考内容：模型支持 reasoning 时单独一块
  • 工具卡片：每个工具调用一张卡片，in_progress → completed / failed，结果正文在卡片里
  • 计划步骤条：todo 清单按状态渲染
  • 写文件 diff 权限弹窗：这是最有价值的一块 —— 落盘前把 diff 交给客户端，你点允许才写

关于权限模型，有个设计取舍值得说：**run_command 不拦**。内核只在「写文件」处有 confirmWrite 钩子，命令没有执行前钩子。所以如果你只想让它读代码、不想让它跑命令，用 --read-only —— 写工具会被整个移出工具表，命令也过一道只读校验。

哪些是它做不到的（诚实版）

M1 有几个明确的限制，列出来免得你踩坑：

限制 原因
没有历史会话 重启客户端等于新建会话，session/load / session/list 都不实现
看不到编辑器里未保存的改动 它直接读写磁盘，不接客户端文件系统（和 CLI 一致）
没有 LSP 诊断 进程里没有语言服务器，写完文件后的「自动读诊断」拿不到东西
没有逐块审阅面板 REVIEW 仍在内存里，但 ACP 客户端没有逐块接受 / 撤销的界面；真正的关口就是那次 diff 权限弹窗
一个进程一个活跃会话 全局态是进程级单例，多 session 会排队而不是并行

这些不是 bug，是当前版本的边界。M2 候选（等有人真的用起来再做）：session/load 复用已有的会话落盘、接客户端 fs/* 以读到未保存内容、透传客户端的 MCP server。

一个容易误会的点：模型切换

在 Zed 里切不了 Luban 的模型，这是设计如此，不是 bug。

Zed 的模型选择器只管它内置的 agent。对外部 ACP agent，「模型 / provider 配置」由 agent 自己拥有 —— ACP v1 也没有标准的模型切换方法。要换模型，改 Luban 自己的配置（~/.luban/config.json 的 provider / model，或 LUBAN_PROVIDER / LUBAN_MODEL 环境变量），改完重启那个线程 —— 进程启动时读一次配置，运行中不热加载。

只影响 Zed 里的 Luban、不动全局的话，把环境变量写进 agent_servers 的 env 字段。

三个入口，一个内核

现在 Luban 有三个入口，共用同一份 extension.js：

入口 宿主 文件读写 诊断 审阅
侧边栏扩展 VS Code 扩展宿主 编辑器 buffer 实时更新 有 有（逐块接受 / 撤销）
luban CLI 终端 真 fs 无 无（写前 diff + y/n）
luban-acp ACP 客户端 真 fs 无 客户端原生 diff 权限弹窗

侧边栏扩展的体验仍然是最完整的（有诊断、有逐块审阅）。ACP 的价值不在于替代它，而在于让不用 VS Code 的人也能用上同一个内核。

自测

协议实现最容易在细节上出错（JSON-RPC 的 id 对应、取消时的 token、权限请求的挂起与恢复），所以配了一套不需要真模型的自测：

测试自己起一个本地 OpenAI 兼容 mock，把 HOME 指到临时目录（绝不碰你真实的 ~/.luban），覆盖 initialize / session/new / 文本流 / 多轮记忆 / 写文件 diff 权限 / ask_question / 取消 / 未知 session 这几条「协议接错才会挂」的路径。

试试看

如果你本来就在用 Zed 或 JetBrains，接上 Luban 大概五分钟。配置写法、参数说明、完整限制清单都在文档里。

遇到问题欢迎提 issue —— 尤其是真机联调的边角，那些往往是自测覆盖不到的。

有 AI 之后，人类的学习时间是否可以缩短了？
可以缩短，但缩短的是入门与检索时间，不是把「真正学会」压缩成捷径。 能缩短的部分 找答案、读文档、试错：以前要翻书、搜论坛、等同事，现在几分钟就能得到方向。 上手与模仿：写第一版代码、理解陌生概念、做练习题的反馈更快。 跨领域摸底：快速建立地图（有哪些概念、怎么连起来），少走冤枉路。 所以「从 0 到能干活」往往确实更快。 很难缩短的部分 长期记忆与熟练：不练、不自己做错题，知识留不住。 判断力：知道何时该信 AI、何时要怀疑、如何验证。 深度与迁移：能在新场景自己设计方案，而不是只会跟着提示改。 责任与品味：工程里的取舍、风格、边界，仍靠经验积累。 AI 像加速器：你踩油门更猛，但车还是你开；不会开的人开得再快也容易撞。 更准确的说法 目标 有 AI 后 「知道大概、能跑通」 明显更快 「考试/认证级熟练」 略快，仍靠练习 「专家级直觉」 几乎不缩短，甚至可能因过度依赖而变慢 结论有 AI 后，人类的学习时间线可以缩短，尤其是入门与效率；但若把「学会」理解成形成可靠能力，核心仍是练习、反思、验证。用得好是放大器；只抄答案，学得更浅、更慢。
