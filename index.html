MES 2026 年第 44 周工作小结

本周（10/26–10/30，约 37 条提交）主线从「流程设计器」切到「小指标公式能力」和「在线操作说明」铺开：周一重构类别树，周二把班组/日/月取数与公式编辑器一口气补齐，周三到周五把手册机制接到计划/报表/小指标/计量多个模块，周五同时推进 eos-nwf 安装向导与联锁 AI 图表。文件改动触达面仍以 mes-workflow、mes-core、mes-measure、mes-web、mes-ai 等为主。

一、小指标公式编辑器（本周主战场）

电厂小指标本周把「能配什么公式」往前推了一大截，编辑器与后端解析一起改：

  • 支持班组 / 日 / 月取数公式，复用既有 DB 解析链路
  • 公式编辑器补齐班组、仪表、条件值类型与级联选择；日/月口径展示完整仪表取值类型
  • W 条件支持班次口径；仪表页增加计算符号列并补齐比较符
  • 修正表元数据加载为空、编辑表单布局与初始化报错；条件值级联的侧线取值与响应式预置
  • 文档与样例同步：按口径显示说明，明确统一入口对 DD / if 的支持边界
  • 周四再加一层：公式编辑器支持 LIMS 取数，补齐 mesdata 脚本；Shiro / 拦截器为 LIMS API 放开匿名访问

单位树也改名为类别树（category tree），和页面语义对齐。

二、在线操作说明机制铺开

「页面右上角能点帮助」继续从试点变成多模块标配：

  • 计划：计划范围 JHFW 页面增加操作说明文档与帮助按钮
  • 报表：报表模块 7 个页面接入在线操作说明
  • 小指标：电厂小指标 7 个页面接入；顺带去掉旧 pi-guide 上多余的帮助按钮
  • 计量：新增计量管理在线手册（6 篇文档 + 9 张截图），并为 15 个计量页面加上使用说明按钮
  • ManualController 支持多级 docId 与资源路径，方便手册按目录组织

三、eos-nwf 与安装向导

独立前端 eos-nwf-web 本周继续打磨部署与交互：

  • 安装向导按系统库自动建角色权限表，减少手工灌库
  • 首页左侧导航支持收缩为图标栏，1366 窄屏更省空间
  • eos2 profile 的 Redis 改为连接本机，方便本机联调

四、AI 联锁与其它支线

  • mes-ai：联锁多日合计经 chart_from_tool 自动附每日趋势图，合计结果旁能直接看走势
  • 应用日志目录切换（logfile），排查多实例日志更方便
  • 树组件 base URL 改为 IP 占位配置，部署时少改死地址

有 AI 之后，人类的学习时间是否可以缩短了？

可以缩短，但缩短的是入门与检索时间，不是把「真正学会」压缩成捷径。

能缩短的部分

  • 找答案、读文档、试错：以前要翻书、搜论坛、等同事，现在几分钟就能得到方向。
  • 上手与模仿：写第一版代码、理解陌生概念、做练习题的反馈更快。
  • 跨领域摸底：快速建立地图（有哪些概念、怎么连起来），少走冤枉路。

所以「从 0 到能干活」往往确实更快。

很难缩短的部分

  • 长期记忆与熟练：不练、不自己做错题，知识留不住。
  • 判断力：知道何时该信 AI、何时要怀疑、如何验证。
  • 深度与迁移：能在新场景自己设计方案，而不是只会跟着提示改。
  • 责任与品味：工程里的取舍、风格、边界，仍靠经验积累。

AI 像加速器：你踩油门更猛，但车还是你开；不会开的人开得再快也容易撞。

更准确的说法

目标 有 AI 后
「知道大概、能跑通」 明显更快
「考试/认证级熟练」 略快，仍靠练习
「专家级直觉」 几乎不缩短，甚至可能因过度依赖而变慢

结论

有 AI 后，人类的学习时间线可以缩短，尤其是入门与效率；但若把「学会」理解成形成可靠能力，核心仍是练习、反思、验证。用得好是放大器；只抄答案，学得更浅、更慢。

同样写着 48GB，T480 和 MacBook、RTX Spark 差多少钱

手里这台是联想 ThinkPad T480（20L6Z3TGUS），CPU 是 i5-8250U。任务管理器里大约 48GB，拆开是两条：32GB（RMSA3330ME88HCF-3200）加 16GB（RMSA3300MH78HBF-2666），实际都跑在 2400。今天拿「同样 48GB」去对 MacBook Pro 和刚开卖的 RTX Spark 笔记本，比的是标价，不是跑分。

价格取 2026-10-17 能公开核对到的国内渠道。促销会变，下面每一行都标了出处。

Mac 这一行来自什么值得买 2026-09-24 的京东自营记录：14 英寸 M5 Pro、48GB+1TB、深空黑，活动价 27874 元，国家补贴 1500 元后 26374 元。苹果 2026-03 新闻稿里，M5 Pro 14 英寸起售价是 17999 元，那是入门内存，不是 48GB。

RTX Spark 这一行来自芯硬件 2026-10-17 对京东自营和官网的汇总。同为 48GB、1TB、20 核的 Surface Laptop Ultra 消费版是 33188 元（夜幕色、Windows 11 专业版），商用版 33588 元。华硕、联想、微星同一天也有 RTX Spark，但公开价要么是 32GB（ProArt P14，20 核 + 1TB，18999 元），要么直接跳到 64GB、128GB，没有另一条干净的 48GB 标价，所以表里只用 Surface。

T480 这一列怎么算

没有给这台机器单独的成交价，用的是重置成本，不是当年买内存的发票。

裸机按 2026 年闲鱼个人直卖：i5-8250U、8GB、256GB、成色好的大约 850–1300 元；带质保的翻新商家大约 1500 元上下（什么值得买对闲鱼和知乎报价的整理）。这台已经是 48GB，裸机行情不含这两根条。

内存按现在重买。2026 年 DDR4 不便宜：台湾零售里 Crucial DDR4-3200 32GB 笔记本条约新台币 9090 元，大约人民币 2000 元出头；大陆有铨兴同规格挂 1599 元。16GB 按容量粗算大约一半。两条一起，大约 2400–3200 元。加上裸机，凑出一台同样 48GB 的 T480，大约 3400–4700 元。下面对比取中间，按 4000 元。

这是估算。内存一周一个价，闲鱼成色差一截价也差一截。

差几倍

按 4000 元重置：

  • MacBook Pro 14，48GB/1TB，国补后 26374 元，大约 6.6 倍。不吃补贴按 27874 元，大约 7 倍。
  • Surface Laptop Ultra，48GB/1TB，33188 元，大约 8.3 倍。商用版 33588 元，差不多。

只拿裸机行情 1200 元去比，会算出二十多倍。那一列把已经插在主板上的 48GB 当成零成本，2026 年不算数。贵的是内存条，不是 2018 年的模具。

反过来说，48GB 这个数字在三台机器上不是同一种东西。

T480 是双通道 DDR4-2400，带宽大约 38GB/s，槽子还在，坏了能换。Mac 的 48GB 是统一内存，CPU 和 GPU 共用，不能加。RTX Spark 的 48GB 是 256-bit LPDDR5X，芯硬件写的峰值带宽 300GB/s，另外还有 CPU 和 GPU 之间 600GB/s 的 NVLink-C2C；满血版标称 FP4 约 1 PFLOPS，用来本地跑大模型。同样四个字，一个是办公内存，一个是显存。

这笔钱买到什么

T480 继续用，买的是键盘、双电池、接口和能自己换件。i5-8250U 在 Windows 11 上写代码、开浏览器够用，本地大模型和剪 4K 不是它的活。C 盘满、常驻太多，会比 CPU 更先让人觉得卡。

26374 元的 MacBook，买的是续航、屏幕、系统和一块能当显存用的 48GB。它不是「内存多 48GB 的 T480」。

33188 元的 Surface，买的是 20 核 Arm CPU 加 6144 个 CUDA 核心，内存带宽比这台 T480 高一个数量级。48GB 在这里是入门档：同系列 128GB 的 Surface 到 48388 元，华硕 ProArt P14 的 128GB 是 35999 元。

所以这台机器现在的位置很具体。内存容量已经和两万六的 Mac、三万三的 RTX Spark 写在同一行；处理器和带宽不在同一行。差出去的五六倍到八倍，是芯片和焊死的高速内存，不是多出来的那几十 GB。

macOS 终端连接 Windows SSH 后崩溃

从 Mac 用系统自带「终端」执行 ssh liuhualiang@192.168.3.9 后，Terminal.app 在同一天崩溃了 5 次。崩溃的是 macOS 终端本身，不是本机 ssh，也不是 Windows 上的 OpenSSH 服务。

现象

时间 进程已运行 异常
13:42 约 26 分钟 EXC_BAD_ACCESS / SIGSEGV，Swift Observation
15:44 约 2 小时 EXC_BREAKPOINT / SIGTRAP，CoreGraphics 分配阴影样式时 malloc 元数据损坏
19:18 约 3.5 小时 EXC_BAD_ACCESS，画屏时 __CFStringCreateImmutableFunnel3
19:31 约 13 分钟 SIGBUS，Terminal 内部同一函数无限递归，栈被打穿
19:44 约 12 分钟 EXC_BAD_ACCESS / PAC，同样死在画屏创建字符串；坏指针里带有空格字节 0x20

进程都是 /System/Applications/Utilities/Terminal.app（2.15，build 488），系统是 macOS 27.0.1。会话不是握手失败立刻断开，而是连上之后跑了一段时间，在重绘窗口时崩溃。

对端

本机客户端是 OpenSSH 10.3。对端横幅是 OpenSSH_for_Windows_9.5。Windows OpenSSH 用 ConPTY 把控制台输出转成 VT 转义序列，这些序列进入 Terminal.app 的解析和绘制路径。

19:31 那次同一栈帧反复出现，是转义序列解析递归没有出口。19:18 和 19:44 两次则是画文字时字符串内存已经被写坏。

社区里有没有同样的报告

没有一份公开报告和这组签名完全一致：macOS 27 的 Terminal 2.15，连 OpenSSH_for_Windows_9.5，死在 CFStringCreateImmutableFunnel3 或 Terminal 内部递归。

相近的记录：

  • openai/codex#39265：Terminal.app 在 SSH 里跑较重的终端界面时反复崩溃，签名包括 EXC_BAD_ACCESS、堆损坏和 CoreText。远程是 Linux。
  • SSH 会话把 Terminal 的 savedState 写坏：画屏时内存损坏，窗口状态被写进 savedState，下次启动接着崩。文中建议改用 iTerm2、Ghostty 或 WezTerm。

Windows 侧另有一类相反的问题：客户端把鼠标上报序列发回 ConPTY，把 conhost 打崩，SSH 会话一起被拆掉（psmux#457）。那是 Windows 进程崩溃，对不上这次的 Terminal.app 报告。

可以换的终端

这台 Mac 上当时只有系统自带终端。下面几个都走自己的模拟器，仍然用本机 ssh：

Ghostty brew install --cask ghostty
WezTerm brew install --cask wezterm

Maven 项目还能像 Sysdeo 那样用 Tomcat 插件启动吗？Eclipse 与 Cursor 选型

早年用 Sysdeo Tomcat Plugin 管「普通 Java EE 工程」很顺手：指定本机 Tomcat、挂上 web 工程、工具栏启停。迁到 Maven、再迁到 Spring Boot / Cursor 之后，常会问三件事：

  1. Maven 项目还能不能像以前那样用 Tomcat 插件启动？
  2. 现在的 Eclipse Tomcat Plugin（Sysdeo 后继）能不能管 Maven？
  3. Cursor 里有没有类似插件管 Maven 项目启动？

下面按结论 → 差异 → IDE 选型 → 实践建议说明。

结论

  1. 可以，但体验和旧「非 Maven Java EE + Sysdeo」不完全一样：Maven 负责依赖与打包，Tomcat 插件负责启动/部署，两者要配合，不能指望只点一下「启动 Tomcat」就自动搞定全部 classpath。
  2. Eclipse Tomcat Plugin（Sysdeo 的维护分支）能管 Maven 项目，并支持 Maven classpath；复杂多模块工程更稳妥的是 m2e + m2e-wtp + WTP Servers。
  3. Cursor 可装 VS Code 系扩展管理外置 Tomcat；对 Spring Boot 工程，日常更推荐 mvn spring-boot:run 或 Java Launch，而不是硬造 Sysdeo 式外挂 Tomcat。

和旧 Sysdeo 非 Maven 项目差在哪

维度 旧普通 Java EE Maven 项目
classpath 手加 lib / 项目引用 由 pom.xml 解析到本地仓库
部署单元 工程目录 / 手工 WAR mvn package 出 WAR/JAR，或 exploded target/...
插件职责 启动 Tomcat + 挂 context 仍可挂 context，但依赖须先被 Maven/IDE 解析好

所以：不是「Maven 就不能用 Tomcat 插件」，而是 「先让 Maven/IDE 建好运行 classpath 与 web 资源，再交给 Tomcat」。

三条常见启动路径

  1. IDE 插件：m2e（或等价工具）解析依赖 → WTP / Eclipse Tomcat Plugin / Community Server Connectors → 外置 Tomcat。接近 Sysdeo 的工具栏体验。
  2. Maven 插件：在 pom 里配 tomcat7-maven-plugin / Cargo 等，跑 mvn tomcat7:run。不依赖 IDE，适合命令行与 CI。
  3. Spring Boot 内嵌 Tomcat：spring-boot-maven-plugin + spring-boot:run（或打可执行 JAR）。许多现代工程（含我们这边的 MES mes-web）日常走这条。

路径 1/2 适合「传统 WAR + 独立 Tomcat」；路径 3 适合「内嵌容器开发」。选型要看项目打包形态，而不是只看有没有装 Tomcat 插件。

Eclipse：Eclipse Tomcat Plugin 能否管 Maven？

能，但别把两条产品线混为一谈。

Eclipse Tomcat Plugin（Sysdeo 后继）

  • Marketplace 名称：Eclipse Tomcat Plugin，仓库见 tomcatplugin/tomcatplugin。
  • 已支持 Maven classpath management。
  • 适合：想轻量「指一个 Tomcat 安装目录 + 挂 web 工程」的开发者。
  • 局限：复杂多模块、provided 作用域的 servlet API、Spring Boot fat JAR/WAR 与「传统 exploded webapp」模型不一致时，容易踩 classpath / ServletContainerInitializer 一类问题。

更推荐的 Eclipse Maven Web 组合

  • M2E + m2e-wtp + WTP Servers（Run on Server）。
  • m2e-wtp 负责把 war 工程配成 Dynamic Web Facet、把依赖装进部署装配。
  • 这才是 Eclipse 生态里管理 Maven WAR → Tomcat 的主流做法。

若工程是 Spring Boot：日常用内嵌 Tomcat；外置 Tomcat 通常另走 WAR 打包（例如独立 pom-war.xml），再交给 WTP 或 Tomcat Plugin 部署。不宜用 Sysdeo 后继插件替代日常的 spring-boot:run。

Cursor：有没有「管理 Maven 项目启动」的插件？

Cursor 兼容 VS Code 扩展市场，没有与 Sysdeo 同级、专门为「大型多模块 Maven」深度定制的官方插件。常用组合：

扩展 作用 备注
Extension Pack for Java / Maven for Java 导入 Maven、跑 goals 基础必装
Community Server Connectors（Red Hat） 管理本地 Tomcat、部署 WAR 较新，倾向替代旧 Tomcat 扩展
Tomcat for Java（adashen） 启停 Tomcat、跑/调试 WAR 偏旧，新项目慎用
Tomcat Auto Deploy 等 保存后同步/热部署 偏传统 WAR

对 Spring Boot 类项目，Cursor 侧更贴合的启动方式：

  1. 终端 / Maven 视图：mvn spring-boot:run -Dspring-boot.run.profiles=...
  2. Java 扩展 Launch：给主类（如 MesApplication）建 launch.json
  3. 外置 Tomcat：仅在需要验证 WAR 产物时，用 Community Server Connectors 部署 target/*.war

不建议在 Cursor 里硬造「Sysdeo 式一键外置 Tomcat」当日常主路径——和内嵌 Tomcat、本地 Docker 中间件工作流容易打架，维护成本高。

结合 Spring Boot / MES 的实践建议

以常见的 Spring Boot 多模块 Web 工程为例：

  • 日常开发：spring-boot:run（内嵌 Tomcat）+ 本机或 Docker 起 MySQL/Redis。
  • Eclipse 怀旧体验：若必须工具栏管 Tomcat，优先 WTP + m2e-wtp 部署 WAR；Sysdeo 后继仅作轻量备选。
  • 正式/生产形态：WAR 打进外置 Tomcat（或现有热补丁流程），与本地插件启动解耦。

一句话：Maven 可以用 Tomcat 插件；Eclipse 后继能管，但复杂工程更信 WTP；Cursor 能管外置 Tomcat，Spring Boot 日常仍优先内嵌启动。
